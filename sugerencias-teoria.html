Cap. 3 — Angular Binding

✅ Los 4 tipos de binding están bien explicados con ejemplos claros.

⚠️ Falta: uso de $event en event binding

El alumnado necesita capturar el valor de un input o el objeto de evento. El parámetro $event aparece en todos los proyectos y no está documentado:

<!-- $event es el objeto de evento nativo o del componente Ionic -->
<ion-input
  (ionInput)="nombre = $event.detail.value">
</ion-input>

<!-- Pasándolo a una función del TS -->
<ion-input
  (ionInput)="onInput($event)">
</ion-input>

⚠️ Falta: nota sobre (ionInput) vs (input) en Ionic

Los componentes Ionic tienen sus propios eventos. (input) es el evento nativo del DOM y no siempre funciona con ion-input; el evento correcto es (ionInput) y el valor se lee con $event.detail.value.

💡 Sugerencia: nota sobre [(ngModel)] y FormsModule

El ejemplo de two-way binding usa [(ngModel)] pero no se explica que requiere importar FormsModule. Además, conviene mencionar que en formularios reactivos (cap. 9) no se usa ngModel, sino [formGroup] / formControlName.

Cap. 4 — Estructuras de control de flujo

✅ @if/@else bien explicado. La sección de @for con el concepto de track es muy completa y práctica.

⚠️ Falta: variables de bloque de @for

Angular expone variables implícitas dentro del @for muy útiles en el proyecto (p.ej. para estilo alternante o numeración):

@for (elemento of elementos(); track elemento.nombre;
     let i = $index, primero = $first, par = $even) {
  <ion-item>{{ i + 1 }}. {{ elemento.nombre }}</ion-item>
}
Variable Valor
$indexÍndice numérico (0-based)
$first / $lasttrue si es el primer / último elemento
$even / $oddtrue si el índice es par / impar
$countNúmero total de elementos en el array

⚠️ Falta: @switch

Es la alternativa a múltiples @else if cuando se compara una sola expresión con varios valores posibles:

@switch (elemento.categoria) {
  @case ('electronica') { <ion-chip color="primary">Electrónica</ion-chip> }
  @case ('ropa')       { <ion-chip color="secondary">Ropa</ion-chip> }
  @default               { <ion-chip>Sin categoría</ion-chip> }
}

Cap. 5 — Navegación

✅ Capítulo muy completo: rutas, lazy loading, parámetros, routerLink, menú lateral y tabs.

⚠️ Falta: pasar datos entre páginas con history.state

El proyecto TA06 (detalle.page.ts) usa este patrón y el alumnado no tiene ninguna referencia teórica para entenderlo. No es el único método, pero es el que usan en la tarea:

// Página origen — enviar datos al navegar
this.router.navigate(['/detalle'], {
  state: { elementoHome: this.elemento }
});

// Página destino — leer datos en ngOnInit
ngOnInit() {
  const state = history.state;
  if (state?.elementoHome) {
    this.elementoDetalle.set(state.elementoHome);
  }
}
⚠️ Limitación: history.state solo funciona con navegación programática (router.navigate). Si el usuario recarga la página, el estado se pierde.

Cap. 6 — Inyección de dependencias

✅ La comparativa constructor vs inject() es clara y bien justificada.

💡 Sugerencia: ejemplo de servicio con signals

Dado que el módulo combina DI y signals, añadir un ejemplo de servicio que expone sus datos como signals ayuda a conectar ambos temas:

import { Injectable, signal, computed } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class ElementosService {
  // Signal privado que solo el servicio modifica
  private _elementos = signal<Elemento[]>([]);

  // Readonly público que los componentes pueden leer
  elementos = this._elementos.asReadonly();
  total     = computed(() => this._elementos().length);

  agregar(e: Elemento) {
    this._elementos.update(lista => [...lista, e]);
  }
}

💡 Sugerencia: mencionar providedIn: 'root'

El capítulo muestra cómo inyectar servicios pero no explica qué hace providedIn: 'root' en el decorador @Injectable. Es la línea que hace que el servicio sea un singleton accesible en toda la app sin registrarlo manualmente.

Cap. 7 — Signal, Computed y Effect

✅ Muy completo: creación, lectura, set/update, computed, effect, flujo y casos de uso.

💡 Sugerencia: signals tipados con objetos e interfaces

Los ejemplos del capítulo usan tipos primitivos (number, string). El proyecto TA06 usa signals de arrays de objetos, que es el caso más frecuente:

// Signal de array de objetos con tipado
elementos = signal<Elemento[]>([]);

// Añadir elemento
this.elementos.update(lista => [...lista, nuevoElemento]);

// Signal que puede ser null (para datos que llegan de navegación)
elementoDetalle = signal<Elemento | null>(null);

// En el template: hay que comprobar que no sea null antes de acceder a sus propiedades
// @if (elementoDetalle()) { {{ elementoDetalle()!.nombre }} }

💡 Sugerencia: signal.asReadonly()

Cuando un signal es propiedad de un componente o servicio y no queremos que se modifique desde fuera, podemos exponer una versión de solo lectura:

private _contador = signal(0);
contador = this._contador.asReadonly(); // no tiene .set() ni .update()

Cap. 9 — Formularios reactivos

✅ Actualizado en sesión anterior: incluye inicialización inline, validators directos, Record<string, unknown> y gestión del envío.

💡 Sugerencia: patchValue() para rellenar formularios

Cuando queremos editar un elemento existente (p.ej. cargar datos de un listado en un formulario), se usa patchValue(). Aparecerá en tareas futuras:

// patchValue: rellena solo los campos indicados (los demás no cambian)
this.formularioElemento.patchValue({
  nombre: elemento.nombre,
  descripcion: elemento.descripcion,
});

// setValue: rellena TODOS los campos; falla si falta alguno
this.formularioElemento.setValue({
  nombre:      elemento.nombre,
  descripcion: elemento.descripcion,
  categoria:   elemento.categoria ?? '',
});

Cap. 10 — Validaciones

✅ Actualizado en sesión anterior: incluye touched, dirty, pristine. Validators integrados y personalizados bien cubiertos.

⚠️ Error frecuente del alumnado: clave del error minlength (minúscula)

El validador se llama Validators.minLength(3) (camelCase), pero la clave del objeto de errores que genera es minlength (todo minúsculas). Causa muchos bugs silenciosos:

// ✅ Correcto: la clave del error es 'minlength' (todo minúsculas)
nombre.errors?.['minlength']

// ❌ Incorrecto: 'minLength' no existe en el objeto de errores
nombre.errors?.['minLength']  // siempre undefined → el @if nunca se activa
Lo mismo ocurre con: maxlength (no maxLength) y requiredtrue (no requiredTrue).

Cap. 11 — Mostrar errores de validación

✅ Actualizado en sesión anterior: incluye markAllAsTouched(), getters de conveniencia, desglose ?.trim() / ?? '' / || undefined.

💡 Sugerencia: mostrar errores en formularios dinámicos

En los formularios dinámicos no hay getters de conveniencia; la forma de acceder a un control es formularioDinamico.get(campo.name). Conviene documentarlo como complemento a la sección de getters:

<!-- En formularios estáticos, usamos un getter -->
@if (nombre.invalid && nombre.touched) { ... }

<!-- En formularios dinámicos, usamos .get() con el nombre del campo -->
@if (formularioDinamico.get(campo.name)?.invalid
  && formularioDinamico.get(campo.name)?.touched) {
  <ion-note color="danger">
    <!-- Para minlength: -->
    Mínimo {{ formularioDinamico.get(campo.name)?.errors?.['minlength']?.requiredLength }} caracteres.
  </ion-note>
}
