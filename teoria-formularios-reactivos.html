¿Qué son los formularios reactivos?

Los formularios reactivos son un enfoque de gestión de formularios en Angular que se basa en la creación y control explícito de la estructura del formulario desde el código, utilizando clases como FormGroup, FormControl y FormBuilder. Su principal finalidad es ofrecer un control total sobre el estado, los valores y la validación de los campos, permitiendo una gestión más predecible y escalable en comparación con otros enfoques. Se utilizan especialmente en aplicaciones donde los formularios son complejos, dinámicos o requieren validaciones avanzadas, como comprobaciones en tiempo real o integración con servicios externos. En general, los formularios reactivos son la opción más adecuada cuando se necesita una mayor robustez, mantenibilidad y capacidad de adaptación dentro de aplicaciones modernas desarrolladas con Angular.

Angular ofrece dos formas de crear formularios:

Característica Template-driven Reactive (nosotros)
Definición En el HTML con ngModel En el TypeScript con FormGroup
Modelo de datos Implícito Explícito y observable
Validación Directivas en el HTML Funciones en el TS
Testing Difícil Fácil
Escalabilidad Formularios simples Formularios complejos

Los formularios reactivos definen toda la estructura y validación en TypeScript. El template solo se encarga de mostrar los campos y los errores.

Ventajas:
  • Control total sobre el modelo de datos.
  • Validación programática: puedes componer validadores como funciones puras.
  • Reactividad: el valor del formulario es un Observable, ideal para escuchar cambios en tiempo real.
  • Testabilidad: al estar en TS, puedes hacer unit tests sin renderizar HTML.

Configuración Inicial

Importar ReactiveFormsModule.

En un componente standalone, se importa directamente en el array imports del componente:

import { ReactiveFormsModule, FormBuilder, FormGroup, Validators } from '@angular/forms';

@Component({
  selector: 'app-home',
  templateUrl: 'home.page.html',
  imports: [
    ReactiveFormsModule,  // ← necesario para [formGroup] y formControlName
    // ...otros imports
  ],
})
export class HomePage { }
⚠️ Importante: Sin ReactiveFormsModule, las directivas [formGroup] y formControlName no funcionarán y Angular mostrará un error.

En Angular, los formularios reactivos se basan en objetos FormGroup y FormControl, en lugar de depender de plantillas (ngModel). Esto permite:

  • Mayor control programático sobre valores y estado.
  • Validaciones declarativas y dinámicas.
  • Suscripción a cambios de valor de forma sencilla (valueChanges).
  • Integración directa con los componentes de Ionic.

Conceptos clave: FormBuilder, FormGroup y FormControl

Clase Descripción
FormControl Representa un campo individual del formulario. Tiene un valor y validadores propios.
FormGroup Representa un grupo de controles. Agrupa múltiples FormControl bajo un mismo objeto.
FormBuilder Servicio auxiliar que simplifica la creación de FormGroup y FormControl.

Formularios estáticos

Los formularios estáticos son aquellos formularios cuyos valores no van a cambiar en el tiempo de ejecución. En este caso creamos nuestro formulario tendrá los valores de nombre, email, password,... y estos valores siempre serán los mismos.

fb = inject(FormBuilder);

// Declaramos la variable,
// Ese ! (non-null assertion) le dice a TypeScript algo así
// "Tranquilo, sé que esta variable se inicializará antes de usarse"
registroForm!: FormGroup;

ngOnInit() {
  this.registroForm = this.fb.group(
    {
      nombre:          ['', [Validators.required, Validators.minLength(3)]],
      email:           ['', [Validators.required, Validators.email]],
      password:        ['', [Validators.required, Validators.minLength(6), passwordStrengthValidator]],
      confirmPassword: ['', Validators.required],
      edad:            [null, [Validators.required, Validators.min(18), Validators.max(99)]],
      aceptaTerminos:  [false, Validators.requiredTrue],
    },
    { validators: passwordMatchValidator } // validador de grupo
  );
}

Desglose de la sintaxis

Cada campo se define como un array: [valorInicial, validadores]

nombre: ['', [Validators.required, Validators.minLength(3)]]
  |      │          │                      │
  |      │          │                      └── segundo validador
  |      │          └── primer validador (o array de validadores)
  |      └── valor inicial (string vacío)
  |__ FormControl: Representa cada campo individual dentro del formulario

Si solo hay un validador, no se necesita un array:

confirmPassword: ['', Validators.required]  // un solo validador, sin []

Inicialización inline vs ngOnInit

En Angular moderno, con inject() disponible, es posible inicializar el FormGroup directamente en la declaración de la propiedad, sin necesitar ngOnInit:

export class HomePage {

  // inject() puede usarse en el cuerpo de la clase, fuera del constructor
  private fb = inject(FormBuilder);

  // El FormGroup se inicializa inline, sin ! ni ngOnInit
  formularioElemento: FormGroup = this.fb.group({
    nombre:      ['', [Validators.required, Validators.minLength(3)]],
    descripcion: ['', [Validators.required, Validators.minLength(5)]],
    categoria:   ['']
  });
}
Estilo Cuándo usarlo
formulario!: FormGroup + ngOnInit Cuando la construcción depende de datos que llegan en ngOnInit (p. ej., parámetros de ruta, datos de un servicio).
formulario: FormGroup = this.fb.group(…) Cuando los campos son conocidos en tiempo de diseño. Más limpio y sin !.

Conectar el formulario al template HTML

[formGroup]

Conecta un elemento <form> con el FormGroup del TypeScript:

<form [formGroup]="registroForm" (ngSubmit)="onSubmit()">
  ...
</form>
  • [formGroup]="registroForm" → vincula este <form> al FormGroup definido en el TS.
  • (ngSubmit)="onSubmit()" → al enviar el formulario, Angular intercepta el evento y llama a onSubmit().

formControlName

Vincula cada campo del template a un FormControl del grupo:

<ion-input formControlName="nombre" type="text"
           label="Nombre *" labelPlacement="stacked"
           fill="outline"></ion-input>
  • formControlName="nombre" → busca un control llamado "nombre" dentro del formGroup padre.
  • El valor del input se sincroniza automáticamente con registroForm.get('nombre').value.

Getters de conveniencia

En lugar de escribir formularioElemento.get('nombre') en cada sitio del template, podemos exponer getters en el TypeScript que actúan como accesos directos:

// TypeScript — getters de conveniencia
// El operador ! (non-null assertion) indica a TS que el control nunca será null.
get nombre()      { return this.formularioElemento.get('nombre')!; }
get descripcion() { return this.formularioElemento.get('descripcion')!; }
get categoria()   { return this.formularioElemento.get('categoria')!; }

Gracias a esto, el template queda mucho más limpio:

<!-- Sin getter: largo y repetido -->
@if (formularioElemento.get('nombre')?.invalid && formularioElemento.get('nombre')?.touched) { ... }

<!-- Con getter: conciso y legible -->
@if (nombre.invalid && nombre.touched) { ... }
Nota: Los getters solo son útiles en formularios estáticos, donde los nombres de los controles son conocidos en tiempo de diseño. En formularios dinámicos se usa formularioDinamico.get(campo.name) con optional chaining (?.).

Formularios dinámicos

⚠ Importante: En los ejemplos anteriores se usa formControlName sin corchetes ([]) porque el valor es un string literal (nombre, email, ... son estáticos y no cambian). Si fuera una variable, usaríamos [formControlName]="miVariable".

En el TS, podemos crear la estructura que va a tener nuestro objeto "campos". Estos valores pueden ser valores leídos desde una API, un JSON,...

TypeScript

import { Component, inject } from '@angular/core';
import { FormBuilder, FormGroup, Validators } from '@angular/forms';

@Component({
  selector: 'app-registro',
  templateUrl: './registro.component.html',
  standalone: true,
})
export class RegistroComponent {
  private fb = inject(FormBuilder);

  registroForm: FormGroup = this.fb.group({});

  campos = [
    { name: 'nombre',    label: 'Nombre',     type: 'text',     validators: ['required', 'minLength:3'] },
    { name: 'email',     label: 'Email',      type: 'email',    validators: ['required', 'email'] },
    { name: 'password',  label: 'Contraseña', type: 'password', validators: ['required', 'minLength:6'] }
  ];

  // construimos los controles dinámicamente en la clase
  initForm() {
    this.campos.forEach(campo => {
      const validators = [];

      if (campo.validators.includes('required')) {
        validators.push(Validators.required);
      }
      if (campo.validators.includes('email')) {
        validators.push(Validators.email);
      }
      const minLengthValidator = campo.validators.find(v => v.startsWith('minLength'));
      if (minLengthValidator) {
        const length = Number(minLengthValidator.split(':')[1]);
        validators.push(Validators.minLength(length));
      }

      this.registroForm.addControl(campo.name, this.fb.control('', validators));
    });
  }

  // Llamada a initForm() en ngOnInit
  ngOnInit() {
    this.initForm();
  }
}

HTML

En nuestro HTML, podemos crear una estructura que se amolde a los valores dinámicos de "campos".

<form [formGroup]="registroForm">

  @for (campo of campos; track campo.name) {
    <ion-item>
      <ion-label position="stacked">{{ campo.label }}</ion-label>

      <ion-input
        [type]="campo.type"
        [formControlName]="campo.name">
      </ion-input>
    </ion-item>

    @if (registroForm.get(campo.name)?.invalid && registroForm.get(campo.name)?.touched) {
      <ion-note color="danger">
        Campo inválido
      </ion-note>
    }
  }

</form>

Si más tarde necesitamos añadir un registro más al objeto campos, no habrá que hacer ninguna modificación en el HTML, por ejemplo si añadimos "teléfono", solo se modificaría el objeto "campos":

campos = [
    { name: 'nombre',    label: 'Nombre',     type: 'text',     validators: ['required', 'minLength:3'] },
    { name: 'email',     label: 'Email',      type: 'email',    validators: ['required', 'email'] },
    { name: 'password',  label: 'Contraseña', type: 'password', validators: ['required', 'minLength:6'] },
    { name: 'telefono', label: 'Teléfono',   type: 'text',     validators: ['required', 'minLength:10'] }
  ];

Validators directos en el array de campos

El ejemplo anterior usa strings como 'required' o 'minLength:3' y después los interpreta manualmente con if/split. Una alternativa más limpia es almacenar directamente los objetos ValidatorFn de Angular en el array, eliminando todo ese código de traducción:

Enfoque validators en el array Construcción del control
String-based ['required', 'minLength:3'] Hay que interpretar los strings manualmente con if/split.
Directo (proyecto) [Validators.required, Validators.minLength(3)] Se pasan directamente a fb.control(). Sin código extra. 
// Los validadores son funciones reales de Angular, no strings
campos = [
  { name: 'nombre',      label: 'Nombre',     type: 'text', validators: [Validators.required, Validators.minLength(3)] },
  { name: 'descripcion', label: 'Descripción', type: 'text', validators: [Validators.required, Validators.minLength(5)] },
  { name: 'categoria',   label: 'Categoría',  type: 'text', validators: [] },
];

// La construcción del FormGroup se simplifica enormemente:
inicializarFormDinamico(): void {
  const group: Record<string, unknown> = {};
  for (const campo of this.campos) {
    group[campo.name] = ['', campo.validators];
  }
  this.formularioDinamico = this.fb.group(group);
}
Ventaja: Al almacenar los ValidatorFn directamente, el bucle de construcción se convierte en un simple for…of: no hay nada que interpretar, y TypeScript comprueba los tipos en tiempo de compilación.

Record<string, unknown>: tipado seguro para grupos dinámicos

Cuando construimos el objeto group para pasárselo a fb.group(), necesitamos declarar su tipo. La opción más habitual es usar el tipo utilitario de TypeScript Record.

¿Qué es Record?

Record<K, V> es un tipo genérico de TypeScript que representa un objeto cuyas claves son de tipo K y cuyos valores son de tipo V. Es equivalente a escribir { [key: K]: V }, pero más conciso.

// Las dos líneas siguientes son equivalentes en TypeScript:
const a: Record<string, unknown> = {};
const b: { [key: string]: unknown } = {};

¿Por qué unknown y no any?

Tipo Comportamiento
any Desactiva completamente el sistema de tipos. TypeScript deja de comprobar ese valor.
unknown Acepta cualquier valor, pero obliga a hacer una comprobación de tipo antes de usarlo. Más seguro.

En nuestro caso necesitamos unknown porque el valor de cada entrada del objeto group es un array [valorInicial, validadores], no un tipo simple; y fb.group() acepta ese formato:

inicializarFormDinamico(): void {
  // Record<string, unknown>: objeto indexado por string; el valor es un array [val, validators]
  const group: Record<string, unknown> = {};

  for (const campo of this.campos) {
    // Clave dinámica = campo.name  ('nombre', 'descripcion', 'categoria'...)
    // Valor          = ['', [validadores]]  → lo mismo que en un fb.group() estático
    group[campo.name] = ['', campo.validators];
  }

  this.formularioDinamico = this.fb.group(group);
}
Resumen:
  • Record<string, unknown> = "objeto con claves string y valores de tipo desconocido".
  • Usamos unknown en vez de any para mantener la seguridad de tipos.
  • Las claves se añaden dinámicamente con notación de corchetes: group[campo.name] = …
  • El resultado se pasa a fb.group(group), que construye el FormGroup completo.

Gestión del envío: markAllAsTouched() y lectura de valores

Cuando el usuario pulsa "Enviar", hay que comprobar si el formulario es válido. Si no lo es, Angular no mostrará los errores a menos que los campos hayan sido tocados (el usuario haya interactuado con ellos). La solución: marcar todos los controles como tocados de golpe.

agregarElemento(): void {
  // 1. Validar: si es inválido, activar todos los errores visualmente y salir
  if (this.formularioElemento.invalid) {
    this.formularioElemento.markAllAsTouched();  // ← muestra TODOS los errores a la vez
    return;
  }

  // 2. Leer los valores: desestructuración del objeto .value
  const { nombre, descripcion, categoria } = this.formularioElemento.value;

  // 3. Limpiar los valores (trim + operadores ?. y ??)
  const nombreLimpio      = nombre?.trim() ?? '';
  const descripcionLimpia = descripcion?.trim() ?? '';
  const categoriaLimpia   = categoria?.trim() || undefined;  // undefined si vacío

  // 4. Usar los valores (por ejemplo, añadir al signal)
  const nuevoElemento = {
    id:          Date.now(),          // id único basado en timestamp
    nombre:      nombreLimpio,
    descripcion: descripcionLimpia,
    categoria:   categoriaLimpia
  };
  this.elementos.update(lista => [...lista, nuevoElemento]);

  // 5. Resetear el formulario
  this.formularioElemento.reset();
}

Operadores clave en la limpieza de valores

Operador Significado Ejemplo
?. Optional chaining: llama al método solo si el valor no es null/undefined. nombre?.trim()
?? Nullish coalescing: devuelve el lado derecho solo si el izquierdo es null/undefined. nombre?.trim() ?? ''
|| OR lógico: devuelve el lado derecho si el izquierdo es falsy (null, undefined, '', 0, false). categoria?.trim() || undefined
⚠ Diferencia ?? vs ||: Con ??, el número 0 o false se conservan (no son null/undefined). Con ||, el 0 se sustituye por el valor de la derecha. Elige según lo que necesites.

Mensajes de error detallados en el template

Cada vez que un validador falla, Angular añade una entrada al objeto errors del control. Podemos acceder a esas entradas en el template para mostrar mensajes específicos:

<!-- Envolvemos la comprobación de errores en un @if externo -->
@if (formularioDinamico.get(campo.name)?.invalid
     && formularioDinamico.get(campo.name)?.touched) {

  <!-- Error de campo obligatorio -->
  @if (formularioDinamico.get(campo.name)?.errors?.['required']) {
    <ion-note color="danger">{{ campo.label }} es obligatorio.</ion-note>
  }

  <!-- Error de longitud mínima, con el número exacto de caracteres requeridos -->
  @if (formularioDinamico.get(campo.name)?.errors?.['minlength']) {
    <ion-note color="danger">
      Mínimo {{ formularioDinamico.get(campo.name)?.errors?.['minlength']?.requiredLength }}
      caracteres.
    </ion-note>
  }
}

Objeto de errores del validador minlength

Cuando el validador Validators.minLength(n) falla, Angular añade al objeto errors una entrada con la clave 'minlength' (todo en minúsculas) que contiene:

{
  minlength: {
    requiredLength: 3,   // el mínimo que pediste
    actualLength:   1    // lo que tiene el campo ahora mismo
  }
}

Por eso en el template podemos escribir errors?.['minlength']?.requiredLength para mostrar el número exacto al usuario, en lugar de hardcodearlo.

⚠ Atención con el nombre de la clave: El validador se llama Validators.minLength (camelCase), pero la clave en el objeto errors es 'minlength' (todo en minúsculas). Lo mismo ocurre con maxlength, pattern, etc.

Resumen de claves de errores comunes

Validators.xxx Clave en errors Propiedades útiles
required 'required' true / false
minLength(n) 'minlength' requiredLength, actualLength
maxLength(n) 'maxlength' requiredLength, actualLength
email 'email' true
min(n) 'min' min, actual
max(n) 'max' max, actual
